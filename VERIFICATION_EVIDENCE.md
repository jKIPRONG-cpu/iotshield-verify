## 1. Method

| | |
|---|---|
| Semantics | Interleaving — exactly one binding element fires per step |
| Exploration | Exhaustive breadth-first over the reachability graph |
| State cap | 400,000 (not reached; both runs closed) |
| CTL evaluation | Fixpoint over the finite structure |
| Liveness | Reported twice: without fairness, and under **weak fairness** |
| Fairness unit | The **binding element** (transition + bound tokens), not the transition |
| LTL fragment | Safety only; `G ¬p` is checked as the invariant `AG ¬p`, which is sound over a finite structure |

**Why liveness is reported twice.** Against an arbitrary scheduler no concurrent
system satisfies a liveness property, because one binding element can be starved
forever. That is not a security defect. Weak fairness — a continuously enabled
binding element must eventually fire — is the standard assumption that makes
liveness meaningful. A property holding *without* fairness is guaranteed
structurally; one holding *only* under fairness depends on a scheduler guarantee.

### VP-05 — Malware Containment

**Property.** `AG (∃d . place(d) = MalwareExecution → AF (place(d) = Isolation))` (CTL, Safety)

Every device that reaches Malware Execution must inevitably reach Isolation. Reachability is not enough — the eventuality has to hold on every path.

**Baseline result.** Failed · under weak fairness: Failed · 5,600 violating states of 15,876

**Counterexample.**

```
  1.       t-receive(GW-1)
  2.       t-auth(GW-1)
  3.       t-analyse(GW-1)
  4.       t-execute(GW-1)
  5.       <antecedent holds here — the eventuality must now follow>
  6.       t-defer(GW-1)
  7.       t-reobserve(GW-1)
  8.       t-reobserve(GW-1)
  9. loop> t-reobserve(GW-1)
```

**Security weakness.** The deferral arc returns a token from Malware Execution to Suspicious Behaviour **without recording an observation**. Because the detector fires only on a second observation, a schedule that always chooses deferral over re-observation keeps the detector's precondition permanently unmet. Detection is therefore never even *enabled*, so the failure is structural rather than a scheduling artefact — weak fairness does not repair it.

**Modification.** A bounded retry counter `att` was added to the device token. The deferral arc is guarded by `[att < MAX_ANALYSIS_ATTEMPTS]` and the detector gains the disjunct `[att >= MAX_ANALYSIS_ATTEMPTS]`. After at most MAX deferrals the detector becomes enabled regardless of the observation count.

**Hardened result.** Failed · under weak fairness: Verified · 1,596 violating states remain

**Interpretation.** Containment now depends only on the scheduler eventually running a continuously-enabled action, which is the weakest assumption any concurrent system needs. The residual unfair-scheduler failure is not a security defect: no concurrent system satisfies liveness against an adversary that can starve an enabled action forever. Stating both readings is what makes the claim precise.

### VP-06 — Data Leakage Prevention

**Property.** `G ¬(∃d . place(d) = Exfiltration ∧ ¬detected(d))` (LTL, Security)

No execution contains a state in which data leaves a device before the detector has ruled on it. Checked as an invariant, which is sound for a safety formula over a finite structure.

**Baseline result.** Failed · 3,332 violating states of 15,876

**Counterexample.**

```
  1.       t-receive(GW-1)
  2.       t-auth(GW-1)
  3.       t-analyse(GW-1)
  4.       t-execute(GW-1)
  5.       t-exfil(GW-1)
  6.       <property violated in the marking above>
```

**Security weakness.** Detection requires two suspicious observations, but the exfiltration arc is enabled after the first. A transfer therefore completes while the detector is still gathering evidence — the leak precedes the verdict.

**Modification.** Two complementary controls. The detector gained an abnormal-volume disjunct `[vol >= VOLUME_THRESHOLD]` so a single anomalous transfer suffices. The exfiltration arc gained an egress hold `[detFired OR obs = 0]`: a device carrying an open suspicion indicator cannot transfer until the detector has ruled. The transition is retained, not deleted — it stays reachable once detection has fired, and legitimate transfers (obs = 0) are untouched.

**Hardened result.** Verified

**Interpretation.** Egress is held pending inspection rather than blocked outright, which is how an inline DLP broker behaves in practice. The property now holds on every path, and it holds without weakening the formula.

## 4. Heterogeneous interaction scenarios

Each row is answered by reachability over a two-device net. A non-exposed target
has no route to compromise other than the lateral-infection transition, so
"propagated" is a proof that the guard admits that class pair, and "blocked" is a
proof that it does not.

| # | Scenario | Guard decision | Reachability | Agrees |
|---|---|---|---|---|
| SC-1 | Compromised gateway → vulnerable actuator (same zone) | route strength 2 overcomes hardening 1 | **propagated** | yes |
| SC-2 | Compromised gateway → hardened industrial controller | route strength 1 does not overcome hardening 2 | blocked | yes |
| SC-3 | Compromised sensor → temperature actuator | route strength 2 overcomes hardening 1 | **propagated** | yes |
| SC-4 | Compromised sensor → smart camera | no route exists from Motion Sensor to Smart Camera | blocked | yes |
| SC-5 | Cross-zone: compromised clinical monitor → plant controller | zone clinical cannot route to plant | blocked | yes |
| SC-6 | Cross-zone permitted: compromised gateway → clinical monitor | route strength 1 overcomes hardening 0 | **propagated** | yes |

**SC-1 — Compromised gateway → vulnerable actuator (same zone).** The gateway holds the management plane and shared credentials, so its route to an actuator is strong (2). The thermostat is only standard-hardened (1). 2 > 1, so propagation is admitted.

**SC-2 — Compromised gateway → hardened industrial controller.** The same compromised gateway, and the plant zone is routable from the building zone. But the gateway→PLC route is weak (1) and the controller is fully hardened (2). 1 > 2 is false, so the guard denies propagation. Reachability alone is not sufficient — the pair relation decides.

**SC-3 — Compromised sensor → temperature actuator.** The interaction raised in supervision. An actuator that consumes a sensor topic without validating the payload gives the sensor a strong route (2) against standard hardening (1). Propagation is admitted — and note the sensor could not reach a camera at all.

**SC-4 — Compromised sensor → smart camera.** Same compromised sensor, same zone, same hardening as the actuator above — but no route exists between these classes (strength 0). The difference in outcome is attributable to device class alone, which is precisely what a state-only colour set could not express.

**SC-5 — Cross-zone: compromised clinical monitor → plant controller.** Segmentation, not susceptibility. The clinical and plant zones are mutually unreachable under the segment policy, so the guard fails on the zone conjunct before susceptibility is ever considered.

**SC-6 — Cross-zone permitted: compromised gateway → clinical monitor.** The building zone adjoins the clinical VLAN, and an unpatched monitor (0) falls to the gateway route (1). Shows the zone relation permitting as well as denying — the control is a policy, not a blanket block.

## 5. Assumptions and limitations

- **Bounded counters.** `att`, `obs` and `vol` are clamped to small ordinals. An
  unbounded counter makes the reachability graph infinite. Verdicts therefore hold
  for the declared bounds, not for arbitrary values.
- **Three devices.** The configuration is the smallest that makes every property
  non-trivial. Guards are evaluated per pair, so a larger fleet multiplies the
  state space without changing any verdict — but that claim is reasoned, not
  itself model-checked.
- **No symmetry reduction.** Devices are distinguishable, which keeps traces
  readable at the cost of a larger graph.
- **Safety-fragment LTL only.** No liveness LTL is attempted.
- **The animation engine is not the verified artefact.** `engine.ts` fires
  transitions simultaneously for on-screen legibility; the checker uses
  interleaving. The two share place and transition names, but only the formal
  model under `formal/` is what these results describe.
- **Synthetic throughout.** The susceptibility matrix encodes documented IoT
  tradecraft but is not calibrated against measured infection data.
